# 正则搜索最终架构

本文记录 ADR-022 的最终结论和可验收边界。它取代曾探索但未完成的 Boost.Regex + ICU 单 matcher 方案，以及更早的 PCRE2/自制代码页 matcher 双后端。

## 1. 结论

- 供应链和执行引擎只有 PCRE2 10.47 8-bit；不引入 Boost.Regex、ICU Regex 或 ICU converter。
- S1 文本在打开时已经解码，并以 UTF-8 存入 QScintilla。它和原始 UTF-8 S2/S3 使用 PCRE2 的 `PCRE2_UTF | PCRE2_UCP` 模式。
- 原始 UTF-16LE/BE、GBK、GB18030、Big5、Shift-JIS 和 Windows-1252 S2/S3 不全文转码。`EncodedRegexCompiler` 只在这些 subject 上把受支持的日志正则子集编译成等价的 PCRE2 byte-mode pattern。
- Literal、Regex、Hex bytes 仍是三个明确模式。非 UTF 适配层不是第二个 matcher，也不是第二套用户语法；不在子集内的表达式在扫描前以短错误拒绝。
- 结果坐标始终是 64 位原始字节范围。显示窗口只做有界解码，不建立全文件 Unicode 正文或 offset map。

## 2. 为什么这样设计

直接把用户表达式逐字符编码成字节还不够：PCRE2 byte mode 默认能从多字节字符的 trail byte 开始，并且 `.`、字符类、零长度推进和 UTF-16 换行都不再代表文本字符。适配层因此把语法节点编译成确定的源编码单元 atom；扫描器在 mmap 上维护单调的字符边界游标，只在完整单元起点调用锚定 PCRE2 匹配。PCRE2 的 first-code-unit/bitmap 和必需 ASCII 前缀只用作不改变语义的候选过滤；命中 range 仍是用户表达式本身的原始字节范围。

这条路径的复杂度被严格限制在“编码一个 scalar、识别一个编码单元、翻译一个已登记语法节点”。它不实现通用 Unicode 数据库、不实现完整正则 VM、不做双向全文解码，也不承担替换。

## 3. 产品语义

### 3.1 UTF-8 subject

S1、Secure Text 和有效 UTF-8 S2/S3 支持 PCRE2 产品方言，包括 Unicode 属性、完整字符类和常规 PCRE2 lookaround/backreference。大小写和 Unicode 分类由同一锁定 PCRE2 提供。

Binary 切换为 Text 后，若当前 UTF-8 投影包含非法单元，PCRE2 使用 invalid-UTF 匹配能力；非法单元可显示、可定位，不能因为一处非法字节拒绝整个文件。Hex 呈现仍按原始字节搜索，不混入文本正则。

### 3.2 非 UTF 原始 subject

覆盖日志分析的子集：

- 直接输入的可表示字符和 `\xNN`、`\x{...}`；
- `.`、`^`、`$`、alternation；
- `*`、`+`、`?`、`{m,n}`；
- 捕获组、非捕获组、命名捕获、编号/命名 backreference；
- positive/negative lookahead；固定长度 ASCII lookbehind；
- ASCII 范围和显式非 ASCII 字符类；
- ASCII 语义的 `\d \D \s \S \w \W \b \B`，以及 `\R`；
- 开头的 `(?i)`、`(?m)`、`(?s)` 及其组合。

明确拒绝：

- `\p{...}`、`\P{...}`、`\X`、`\C` 等依赖完整 Unicode 属性/字素语义的节点；
- 非 ASCII 范围，例如 `[一-龥]`；应写显式字符或 alternation；
- 多字节或可变长度 lookbehind；
- recursion/subroutine、callout、条件组、控制 verb、locale/collation 等高级结构；
- 展开后超过 256 KiB 的 pattern；
- 不区分大小写 backreference 的跨大小写等价保证。普通字面字符会逐 scalar 展开大小写变体，PCRE2 byte caseless 表永不作用于多字节 trail byte。

错误必须指出表达式附近的位置和不支持的结构，并保持短小；完整解释放在 tooltip/文档，不把查找框撑宽。

### 3.3 整词

- 西文、数字和下划线使用 word boundary。
- 中文、日文、韩文、注音等不依赖空格分词的脚本，Literal 整词按完整短语匹配，不错误要求短语两侧是空白。
- 非 UTF 路径中的 `\w/\b` 是明确的 ASCII 日志语义；不声称是 Unicode 分词。

## 4. 执行与正确性

- `Pcre2Regex` 是唯一执行器。UTF 与 generated byte pattern 均启用 match/depth/heap 资源上限并尽可能 JIT；取消与进度在有界 offset window/候选边界检查，不插入逐 pattern position 的 auto-callout。
- Find All 在稳定 mmap 或 patch 临时快照上顺序 global match。任意正则不使用固定 overlap 分块，因为其最大跨度可能无界。
- 零长度匹配先尝试同位置非空 alternative，再按一个完整 UTF-8 code point 或源编码单元前进。
- Find Next 从当前边界开始，第一处到达即停止；它是独立的 Highest-priority 任务，可与后台 Find All 并行，但不私建线程或第二导航池。
- Find Previous 在没有已建索引时必须从权威起点扫描并保留最近一处；不能用固定回看窗口换取伪即时结果。
- S2/S3 原始编码视图只读。编码转换走“另存为所选编码，成功后打开新文件”，因此 raw regex replacement 不需要第二套捕获回映射。

## 5. 任务调度

- 所有非 UI 串行耗时工作进入 `AsyncTaskManager` 和唯一 `AsyncThreadPool`；应用代码不得创建 `QThread`、私有 `QThreadPool` 或 `std::thread`。
- 应用总 worker 上限为 `clamp(logicalProcessors - 1, 2, 12)`。其中 1 个是计入总额的保留安全 lane，串行执行持有 QObject 状态的加解密/KDBX 操作；其余容量是通用优先级池。批量行扫描也使用中央池，并在通常情况下保留一个交互槽。
- Highest：安全/数据完整性提交、解锁/加解密、Find Next/Previous；High：用户发起的 Find All 和普通即时操作；Normal/Low：行索引补扫/预扫；Lowest：字符统计和用户无需立即看到的维护。
- QThreadPool 不能安全暂停任意正在执行的 C++ 栈。所谓抢占是协作式的：任务切成有界段、在段边界重新进入优先级队列，并在内循环检查 cancel/yield；原子提交阶段不可暂停。
- 有进度的任务提供 ETA。预计总耗时或实际耗时超过 30 秒时，状态栏后台任务位置只弹一次非阻塞气泡，引导用户打开任务中心继续或取消。

## 6. 结果 Dock 与导航

- 文件组行和内容行使用同一列模型；位置/文件列与上下文列起点一致。
- 绘制先保证关键词完整可见，再从远端裁剪前后文。Hex 与 Text 使用相同的 inline range 布局。
- hover/selected 背景覆盖整行，关键词高亮绘制在状态背景上，不能出现中间和左右基线错位。
- 双击只改变视图/selection，不改变正文、modified 或 content revision。只有真实编辑、重新解释编码或目标关闭才使相应结果 stale。

## 7. 验收矩阵

必须同时通过：

1. `test_pcre2_regex`：所有登记编码、边界、零长度、跨 1 MiB 进度窗、捕获/lookaround、拒绝项和取消。
2. `test_largefile_encoded_search`：真实 LargeFileSearch 的 GBK regex/literal/whole-word、trail-byte 防误命中、渐进首批和异步定向导航。
3. GUI：S1 首条异步导航；S2/S3 UTF-8 与至少一个非 UTF 原始编码；Binary Text/Hex；中文整词；Dock 窄宽、hover、selected、双击不失效；全量任务与导航并发；线程上限和 30 秒气泡。
4. clean offline build、供应链校验和无私建线程静态门禁。仓库中不得残留 Boost.Regex/ICU 目标、源码、锁项、SBOM 项或 About 文案。

## 8. 非目标

- 不用完整 Unicode 属性去扩张非 UTF 子集；需要该能力时，用户应先按现有另存为流程转换为 UTF-8。
- 不为正则建立全文件转码副本或全量位置映射。
- 不引入第二个执行引擎来追求表面上的“所有编码完整同语法”。
- 不实现危险的线程强制挂起/恢复。
